## Functional requirements

1. Add `install-ctl guidance get <repository-url>` as a new subcommand, additive to the existing `plan`/`install`/`autofix` subcommands, which it must not modify.
2. Required inputs: the source repository URL (positional) and `--select <id>...` (repeatable, required, same as existing `GuidanceArgs.select`).
3. Optional inputs, each with a documented default:
   - `--profile <repo-relative-path>`: resolved inside the freshly cloned checkout. When omitted, every `--select` value is treated as a bare repo-relative source path and synthesized into an implicit single-item direct-corpus profile (`profile.id = "get"`, one `[[corpus]]` per selected path, `paths = [<that path>]`).
   - `--target <local-repo>`: defaults to `.` (the current working directory).
   - `--destination-scope`/`--destination-path`: same semantics and defaults as `plan`/`install` today.
   - `--keep-checkout`: when set, the managed clone directory is not deleted after the command finishes; its path is printed.
   - `--json`: same machine-output behavior as `plan`/`install`.
4. Clone step: shell out to the system `git` binary as `git clone --depth 1 <repository-url> <managed-temp-dir>`, using a small local `run_git`/`git_command`-style helper mirroring `workflow-tools/session/crates/worktree-ctl/src/git.rs` (Windows extended-length-path normalization included). Do not add a `git2`/`gix` dependency.
5. After cloning, `get` must: load or synthesize the profile, call the existing `build_plan` unchanged, print the plan the same way `plan`/`install` do, and refuse to install (non-zero exit) when the plan is blocking — identical behavior to `install` today, just with the extra fetch step in front.
6. On success or on a blocking plan, delete the managed clone directory unless `--keep-checkout` was given. Deletion must not touch `--target` (the destination repository) under any circumstances.
7. A clone failure (git binary missing, invalid URL, network failure, non-zero git exit) must produce an actionable error naming the failed step and must not attempt to plan or install with a partial/corrupt checkout.
8. `--select` combined with `--profile` uses the profile's declared corpus ids exactly like `plan`/`install` today (no behavior change for that path); only the no-`--profile` path is new.

## Safety requirements

- No implicit write outside the managed temp directory and the already-existing containment/traversal checks each `install` write already performs.
- The synthesized implicit profile must go through the same `validate_repo_relative` checks as any other profile-declared path (reject absolute paths, traversal, etc.) — no bypass of existing validation for the profile-less path.
- Cleanup of the managed checkout must be resilient to a prior blocking/error exit (a failed plan or install must still clean up unless `--keep-checkout`).
