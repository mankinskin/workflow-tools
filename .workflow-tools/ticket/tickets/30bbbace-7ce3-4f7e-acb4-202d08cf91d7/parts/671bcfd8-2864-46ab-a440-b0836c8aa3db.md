# Dependency resolution: shared operation journal

## Confirmed decision (2026-09-09)

Keep `depends_on = 73b2cd22-942b-4205-86e5-333df2373211`.

W6.1 needs the shared operation-journal foundation because Spec v2 migration changes persisted state and must provide consistent preflight, apply, interruption recovery, resume, and rollback behavior. W6.1 consumes that generic facility; W6.1 must not create a spec-only journal format, storage/index path, or a second recovery protocol.

## Upstream purpose

The dependency is intentionally the parent tracker rather than only one completed design ticket. Ticket `6c859ac3-14c9-4d9d-b428-5b0cca03e23a` is done and defines the `OperationJournal` envelope and ownership boundary. Parent ticket `73b2cd22-942b-4205-86e5-333df2373211` remains the integration gate for the shared implementation across domains, including ticket `35cd05c1-45f7-4d65-b943-7c000570928f` adapting move-kernel journals to the generic envelope.

## W6.1 integration boundary

When the parent tracker reaches its shared-journal completion condition, W6.1 uses the established contract to journal spec migration and multi-file writes. W6.1 owns only spec-domain adapters, migration-map validation, and CLI/MCP exposure of the shared preflight/apply/resume/rollback behavior. The shared envelope, journal storage/index architecture, and cross-domain move-kernel adaptation remain upstream ownership.

## Acceptance implication

The existing W6.1 criteria requiring dry-run, collision, resume, rollback, and recoverable multi-file writes are satisfied through the shared journal contract plus the spec-domain adapter. A locally invented journal is explicitly non-conforming.
