## Session-record checkpoints

`worktree-ctl` may checkpoint a dirty worktree only when every dirty superproject path is within `.session/sessions/<owning-session-id>/`, where `<owning-session-id>` is the nested worktree directory UUID and that session record declares the same `session_id`. The checkpoint stages only that directory and uses a fixed tool-owned commit message. Any other superproject path, any submodule dirty state, a missing/malformed session record, or a mismatched session id remains blocking.

Checkpointing must run before clean/remove safety evaluation and before rebase/merge dirty guards, so session-only worktrees can be synchronized and later reclaimed after their session becomes inactive. It does not release or reassign active sessions itself.
