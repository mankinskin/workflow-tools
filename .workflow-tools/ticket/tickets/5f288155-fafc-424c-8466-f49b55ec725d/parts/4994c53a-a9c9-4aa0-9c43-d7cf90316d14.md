## Functional requirements

1. Document the complete `install-ctl guidance` command family: profile/source input, selection, plan, install, audit interaction, autofix plan/apply, destination scopes, confirmation, dry-run, and report output.
2. Document the profile contract for direct corpus/value profiles and recipes that download, generate, or compile artifacts, including permissions, staging, reproducibility, and failure behavior.
3. Document typed dependency edges, supported guidance roots, non-guidance blocking classes, nested/cross-repository classification, unsupported/unsafe diagnostics, and URL/fragment handling.
4. Document destination containment and traversal protections, platform-specific repository/user/system roots, explicit-path rules, submodule preference, canonical fallback, and relative-reference rewriting.
5. Document the mutation boundary: plan and normal detection are read-only, install consumes a clean validated plan, autofix requires explicit apply/confirmation, and the hook remains hard-blocking with the documented bypass.
6. Document deterministic fixture manifests, expected-result assertions, Docker validation, and the separately labelled network smoke test.
7. Keep the generated command catalog synchronized with runtime registry changes and avoid claiming that user-created profiles are registry artifacts.
8. Link all documentation to the owning tickets/work packages using portable guidance-only references; no ticket/spec/code link may be introduced into publishable guidance.
